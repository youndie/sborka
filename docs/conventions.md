# Плагины

Каждый плагин настраивает то, что уже подключил модуль, и **сам не подключает ни Kotlin, ни Compose,
ни AGP**. Модуль пишет `alias(libs.plugins.kotlinMultiplatform)` со своей версией из своего каталога,
а sborka реагирует через `plugins.withId`. Иначе любой апгрейд Kotlin в любом репозитории ждал бы
релиза sborka.

Исключение одно — ktlint: sborka его подключает, потому что «какой ktlint у нас» это ровно то общее
решение, ради которого репозиторий и заведён.

## `io.github.youndie.sborka.settings` — плагин настроек

Применяется в `settings.gradle.kts`. Делает три вещи.

**Репозитории с фильтрами контента, и все фильтрованные — до нефильтрованного.** Репозиторий,
объявленный без фильтра, спрашивается о *каждой* координате, которую резолвит сборка: это лишний
round-trip на каждый промах и — что хуже — шанс, что на чужую группу ответит не тот сервер.

Порядок при этом не косметика. Gradle спрашивает репозитории в порядке объявления и останавливается
на первом ответившем, а фильтр не делает репозиторий дешевле — он делает его **пропускаемым** для
координат, которых тот не заявлял. Значит фильтрованный репозиторий стоит ноль, когда он первый, и
всё, когда он последний: с `mavenCentral()` перед снапшот-сервером каждая первая-сторонняя
координата платила поход на Central, обязанный промахнуться. Промахнуться вежливо он тоже
не обязан — проверка релиза sborka однажды упала на `ru.workinprogress.sborka:catalog` (координата
тех времён) с `Received status code 429 from server: Too Many Requests`.

Настроить можно только сторону резолва. `pluginManagement` вычисляется до применения любого
settings-плагина — включая этот, который сам через него и достаётся, — поэтому снапшот-репозиторий
там приходится выписывать руками. Строки в [migration.md](migration.md).

**Каталог `wip`.** Опубликованный каталог версий, которые нескольким репозиториям приходится держать
одинаковыми. Именно `wip`, а не `libs`: `libs` остаётся своим у каждого репозитория.

Версия каталога — версия самого плагина, зашитая в jar при сборке. Второе число, написанное рядом
руками, — это число, которое разъедется.

**Версия Gradle.** Ключ `gradle` в каталоге — единственное место, где решается, на каком Gradle стоит
портфель. Отдать её потребителю как остальные версии нельзя: `gradlew` читает
`gradle-wrapper.properties` раньше, чем существует хоть один плагин, поэтому число по-прежнему пишется
в wrapper каждого репозитория. Плагин настроек знает ключ (он зашит в jar) и **предупреждает**, если
сборка идёт на другом Gradle; не падает, потому что пин sborka и wrapper часто двигаются разными PR.
Правило Renovate для Gradle в `default.json` и собственный wrapper sborka сверяются с ключом задачей
`verifyGradleVersion` в `check` — переезд на новый Gradle это правка ключа, правила и wrapper-а sborka
одним PR, а потребителей дальше везёт Renovate. Правило держит Gradle **дважды** — wrapper (datasource
`gradle-version`) и официальный образ `gradle:<версия>-jdk25-noble`, в котором собирают Dockerfile-ы
(datasource `docker`), — и находится проверкой именно по этой форме. Пока оно совпадало по менеджеру
`gradle-wrapper`, wrapper стоял на 9.7.x, а образ Renovate уже предлагал 9.8.0.

**Проверка `.editorconfig`.** См. `sborka.lint` ниже. Живёт здесь, а не там, потому что
`.editorconfig` — один файл на репозиторий, значит и проверка одна на репозиторий; проверка, которая
срабатывает только если кто-то не забыл применить модульный плагин к корневому проекту, — это
проверка, которая молча не срабатывает.

| свойство | по умолчанию | что делает |
|---|---|---|
| `sborka.repositoriesMode` | `FAIL_ON_PROJECT_REPOS` | `PREFER_SETTINGS` — для репозитория с таргетами `js`/`wasmJs`: репозиторий для дистрибутива Node объявляет не модуль, а сам Kotlin-плагин, и отказ ловит сборку на репозитории, которого никто в ней не писал |
| `sborka.catalog` | `on` | `off` — не подключать каталог `wip` |
| `sborka.catalogVersion` | версия плагина | взять другую версию каталога |
| `sborka.catalogRepository` | — | дополнительный maven-репозиторий для группы `io.github.youndie.sborka` |
| `sborka.editorconfig` | — | `custom` — этот репозиторий отличается намеренно, не проверять |

Проверка требует, чтобы файл **начинался** с эталона, а не совпадал с ним целиком. Общие правила
обязаны быть на месте и неотредактированными; что репозиторий дописывает ниже — его дело, и один
такой уже есть: там вендоренная спецификация сравнивается тестами побайтово, поэтому секция
`[docs/spec/**]` выключает для этого дерева правила про пробелы. Требование полного совпадения
заставило бы этот репозиторий отказаться от общего стиля целиком ради одной нужной секции.
`updateEditorconfig` переписывает только голову и сохраняет хвост; файл, голова которого не эталон,
он трогать отказывается — классифицировать чужие строки он не может.

### `kapkanMethodSizes` — что JIT просят заинлайнить

Задача на корневом проекте, **не входит в `check`**. Читает те же class-файлы, что и `kapkanJoins`,
и печатает методы, чьё тело длиннее порогов, по которым C2 решает, что инлайнить, — отчёт в
`build/reports/kapkan/method-sizes.txt`.

| флаг | байт | что решает |
|---|---|---|
| `MaxInlineSize` | 35 | холодный callee длиннее не инлайнится |
| `FreqInlineSize` | 325 | горячий callee длиннее не инлайнится |
| `InlineSmallCode` | 2500 | скомпилированный callee крупнее не инлайнится повторно |
| `HugeMethodLimit` | 8000 | метод длиннее не компилируется вовсе |

Значения — этого JDK, снятые `-XX:+PrintFlagsFinal` на 25.0.4, а не по памяти: это product-флаги, они
двигаются между релизами. Отчёт печатает число рядом с флагом, чтобы читающий не сверялся с чужим.

**Почему не ktlint.** Пороги считаются в байтах скомпилированного тела, а два котлиновских источника
раздувания в исходнике не видны: `suspend`-функция становится машиной состояний, `inline`-функция
копируется в вызывающего. На стенде zavarnik `Pricing.quote` читается как десяток строк и
компилируется в 1827 байт.

**Порог отчёта — `FreqInlineSize`, а не `MaxInlineSize`.** 35 байт накрывают почти любой метод,
который что-то делает, а отчёт, называющий почти всё, — счётчик, а не находка. Тот же довод, что
держит `kapkanJoins` вне `check`.

**Порог срабатывает в горячем пути — это измерено 07.09.2026** на стенде zavarnik под нагрузкой
(31 418 rps на `/business` в чистом окне, 36 692 во втором; JDK 25.0.4, `-XX:+PrintCompilation -XX:+PrintInlining`). Из 858 отказов
«too big» в логе компилятора пять называют код стенда, и все они — «hot method too big»:

| метод | байт | отказов |
|---|---|---|
| `bench.Pricing::quote` | 1827 | 2 |
| `bench.MainKt$main$1$2$9::invokeSuspend` | 816 | 2 |
| `bench.Order$$serializer::deserialize` | 374 | 1 |

Счёт — нижняя граница: потоки компилятора пишут в один поток вывода вперемешку, и имя, разорванное
между строками, в счёт не попадает.

То есть `invokeSuspend` **предлагают** к инлайнингу, а не только компилируют как корень — довод,
который стоял здесь раньше, был неверен. Из десяти методов за порогом отказ достался трём.

**Тем же проходом печатаются ещё два ответа**, раз class-файлы уже открыты:

- **паттерн, собираемый на каждый вызов**: `Regex(…)` или `Pattern.compile(…)` в теле метода.
  В `<clinit>` он собирается один раз, в методе — на каждый вход; `<clinit>` поэтому не считается.
  На стенде zavarnik это был самый крупный пользовательский источник аллокаций — 6,5 % байт;
- **`Intrinsics.check*` на метод** — счётчик, а не список: сколько всего мест и у каких тел их
  больше всего. Это то, что убрали бы `-Xno-param-assertions` и `-Xno-call-assertions`. Списком
  здесь была бы половина сборки.

Обе цифры считаются обходом инструкций, а не поиском байтов: операнд может содержать любой байт, и
единственный способ знать, что `0xB8` — это `invokestatic`, а не хвост `ldc2_w`, — дойти до него,
перешагнув всё предыдущее. **Тело, на котором обход не сошёлся, называется по имени, а не считается
нулём**: иначе два ответа выше подменяются молчаливым нулём.

**Чего это всё равно не делает.** Отказ инлайнить — не измеренная цена: сервис с уменьшенными телами
никто не мерил, так что «JIT отказался» и «здесь медленно» — два разных утверждения, и доказано
первое. Поэтому задача называет методы и флаги и оставляет чтение человеку.

### `kapkanJoins` — что этот репозиторий построил и ни разу не вызвал

Задача на корневом проекте, **не входит в `check`**. Читает скомпилированные class-файлы всех
модулей, строит по constant pool граф ссылок и печатает объявления, которые не упоминает ни один
другой файл, — в компиляторном формате плюс отчёт в `build/reports/kapkan/joins.txt`.

Две кучи, и вторая — интереснее: **`only tests mention it`** это ровно форма всех четырёх находок,
ради которых правило написано (`PaymentGateway.capture` реализован и не вызван, `SendReceiptUseCase`
написан, покрыт тестом и не зарегистрирован ни в одном DI-модуле, sign-in доказан с двух концов и не
соединён, рендереры kompot без продюсера и консьюмера).

**Почему в settings-плагине.** Причин две. Общая с `checkEditorconfig`: это одна задача на
репозиторий, а задача, висящая на модульном плагине, работает только там, где его кто-то не забыл
применить к корню. Своя: применение **проектной** конвенции к корневому проекту кладёт jar конвенций
на classpath всех модулей, и модуль, просящий плагин с версией, получает «already on the classpath
with an unknown version».

Спрашивается не одно и то же у типа и у функции. У типа — «упоминает ли его хоть один **другой
файл**»; у функции — «вызывает ли её хоть кто-нибудь, включая её собственный файл». Разница — это
разделение Screen/Content: `Content`-компоузабл вызывает `Screen` рядом с ним и больше никто,
тринадцать раз на приложение, и все тринадцать корректны. Не теряется ничего: `PaymentGateway.capture`
не вызывался вообще ниоткуда, включая свой файл.

**Почему не в `check`.** Замерено на полностью собранной shashki: **29 находок** на 333 типа и 253
функции, 1563 прочитанных class-файла. Дефект среди них не каждая: `inline`-функция не оставляет
ссылки (её тело копируется в вызов), `const val` сворачивается в место использования, а объявить
помощника рядом с единственным пользователем — идиома Kotlin. Шумное правило переезжает в отчёт, а не
смягчается. Двадцать две из двадцати девяти — куча «только тесты», и она читается: `PaymentGateway.
activeHolds`, `DriverReservations.reservedFor`, `DegradationCounter.total` — публичная поверхность,
которой пользуются только её же тесты.

**Две вещи, без которых счёт был бы враньём, и обе измерены, а не предположены:**

- **Kotlin манглит JVM-имя функции, у которой в сигнатуре value class.** `drawTileRoads` в байткоде —
  `drawTileRoads-Rg1IO4c`; сравнение с исходным именем объявляет ненайденным всё, что принимает
  `Color`, `Dp` или `Duration`. На shashki это было пять находок из первых шести, и все пять ложные.
- **Вызов компилируется против типа, который держит вызывающий.** `viewport.toGeo(…)` называет
  `MapViewport.toGeo`, хотя `toGeo` объявлен на интерфейсе `Projection`, — поэтому задача читает из
  class-файла суперкласс и интерфейсы и раскрывает вызов вверх по иерархии. Без этого находкой была бы
  каждая функция каждого интерфейса.

**Чего задача не видит, и это измерено, а не предположено:** регистрация в Koin-модуле **является**
ссылкой (лямбда `single { … }` компилируется в класс, в constant pool которого лежит конструктор), а
сгенерированный код считается ссылающимся — поэтому рендереры KSP-реестра в список не попадают, а сам
реестр попадает, и именно там B-32 и был виден. Читается только JVM-вывод: klib нативных и wasm-таргетов
держит ссылки внутри сериализованного IR, у которого нет поддерживаемого ридера.

**Подавление — без ktlint-овского префикса:**

```kotlin
@Suppress("kapkan:joined-at-neither-end", "a Gradle plugin is found by id, so no code names the class")
```

ktlint проверяет id внутри `@Suppress` по загруженным им правилам и отказывается от незнакомого — а
это правило он не загружает, оно задача Gradle. Причину рядом всё равно требует ktlint:
`kapkan:suppression-needs-a-reason` знает оба префикса.

## `io.github.youndie.sborka.base`

Координата, версия, тулчейн. Подключается остальными; отдельно нужен только приложению, которому не
нужны ни публикация, ни `explicitApi`.

Версия ставится **на проект**, а не только на публикацию, и разница из сборки не видна: имена
архивов берутся из версии проекта, поэтому публикация с полным номером отгружает файлы, названные
запасной версией. Резолв работает — метаданные указывают на правильный url, — а файл просто
неправильно назван по прибытии, и два релиза становятся неразличимы для всего, что читает имена.

| свойство | по умолчанию | что делает |
|---|---|---|
| `sborka.group` | **обязательно** | maven-группа всех модулей репозитория |
| `version` (в `gradle.properties`) | `0.1.0-SNAPSHOT` | голова версии; `-PVERSION` из CI перебивает |
| `sborka.jvmToolchain` | `25` | JDK, которым всё компилируется |
| `sborka.serializeWebLinks` | `true` | линковки Kotlin/Wasm и Kotlin/JS — по одной на сборку (ниже) |

Группа не имеет значения по умолчанию намеренно: шесть модулей одного репозитория когда-то уехали
под группой, выведенной из имени каталога, и это всплыло на аплоаде — PUT не по тому пути, после
того как всё скомпилировалось и прошло тесты.

**Где версию считает `determine-version`, голова — простое `X.Y.Z`.** Экшен приписывает номер
прогона к тому, что прочитал, и из `0.1.0-SNAPSHOT` получилось бы `0.1.0-SNAPSHOT.1`. Это не
нумерованный снапшот `X.Y.Z.N`, не релиз и даже не maven-снапшот, потому что тот обязан
*кончаться* на `-SNAPSHOT`: ровно так ушла первая публикация kontainer (`e18d6bb`). Поэтому экшен
такую голову отвергает и в сообщении называет исправление (#119). Значение по умолчанию из
таблицы — запасная версия для сборки, которой `-PVERSION` не передают вовсе. Ей `-SNAPSHOT`
подходит, и mongkn держит его нарочно.

**Голова называет следующий релиз, а не выпущенный.** Порядок версий Maven, которому следует
Renovate, ставит `X.Y.Z.N` выше `X.Y.Z`, поэтому голова, оставшаяся на выпущенном номере после тега,
выпускает сборки, которые обгоняют релиз и выглядят его пересборкой. Так публиковали после релиза
appframe, viddik, chronik и zavarnik, пока головы не подняли (appframe#55, viddik#59, chronik#32,
zavarnik#22, oldge-ui#14). `determine-version` спрашивает у `origin` репозитория, из которого читает
голову, есть ли тег `v<голова>` (`git ls-remote`: checkout тегов не приносит), и если есть —
отказывает: версию не пишет, в ошибке называет следующий патч, на который голову поднять, и шаг 5
скилла `kmp-library-release`, а тег кладёт в выход `tagged`, чтобы вызывающий с
`continue-on-error` отличал этот отказ от любого другого. Сначала (#131) это было предупреждение:
у oldge-ui голова стояла на выпущенном `0.1.0`, и отказ сделал бы красным его следующий push.
Отказом оно стало, когда таких вызывающих не осталось (перед вливанием проверены все десять).
Проверяется только форма `v<голова>`: релизов без `v` в портфеле нет, а нумерованные теги прогонов
(`vX.Y.Z.N`, как у kafkakn) — другой ref. `origin`, который не ответил, — предупреждение, а не отказ:
сетевая ошибка не должна останавливать публикацию.

### Линковки Kotlin/Wasm и Kotlin/JS — по одной на сборку

Каждая задача типа `KotlinJsIrLink` (`compile*ExecutableKotlinWasmJs`, `compile*ExecutableKotlinJs`)
в модуле с `org.jetbrains.kotlin.multiplatform` занимает один общий слот: `BuildService` с
`maxParallelUsages = 1`, один на сборку. Пока одна линкуется, остальные ждут. Модуль без
js/wasm-исполняемого не затронут: у него нет задачи, которая просила бы слот, а сервис регистрирует
первая линковка, так что в сборке совсем без них его нет. С configuration cache совместимо: сервис —
обычная зависимость задачи, ничего не читается на исполнении из проекта.

**Почему (#132).** Все линковки сборки идут внутри одного демона Kotlin и делят его кучу. Одна
Compose-линковка держит 0,7–0,9 ГБ живых данных. В kompot восемь параллельных линковок заполнили
унаследованные `-Xmx3g`: демон час провёл в полных сборках мусора на 2,78 из 2,9 ГБ и упал с
`GC overhead limit exceeded` (kompot#183). В shashki три тестовые линковки упирались в те же 3 ГБ, и
холодная сборка падала в 4 из 11 прогонов CI (shashki#37). Тёплая сборка берёт линковки из кэша и этого не показывает,
поэтому снаружи это выглядит как красный, который перезапуск делает зелёным.

Чинили двумя способами. shashki подняла кучу демона до измеренных 5 ГБ; kompot поставил очередь
с одним слотом и остался на 3 ГБ с пиком около 2 ГБ. Сюда переехала очередь: она держит при любом
числе линкующих модулей и на любой машине, а размер кучи приходится перемерять с каждым модулем,
который начинает линковаться.

**По типу задачи, а не по списку модулей** — модуль, который начнёт линковаться завтра, встанет в
очередь сам. **JS вместе с wasm:** тип задачи общий, и механизм тот же — вся программа понижается
внутри того же демона, — поэтому js-линковка рядом с wasm-линковкой делит кучу так же, как две
wasm-линковки. Отдельно js-линковки не измерялись.

**Цена по времени.**

| где | линковок | без очереди | по одной |
|---|---|---|---|
| shashki, холодный `check` + дистрибутивы, GitHub-раннер 4 ядра / 16 ГБ, по 3 прогона | 5 + 2 | 413 + 199 с | 401 + 206 с (куча 5 ГБ), 398 + 207 с (3 ГБ) |
| kompot, полная сборка без кэша (`--rerun-tasks`), Linux-машина 20 ядер, по 3 прогона | 27, из них 8 production | 251 с в среднем (две за раз) | 322 с в среднем |

На четырёх ядрах очередь ничего не стоит: параллельные линковки дерутся за те же ядра, суммарное
время линковок в очереди падает с 394 до 240 с, и стена не сдвигается за пределы разброса между
раннерами (медианы; сырые строки и метод — [link-queue/measure-links-2026-10-02.txt](research/link-queue/measure-links-2026-10-02.txt)).
С очередью shashki прошла холодную сборку и на 3 ГБ (`-Pkotlin.daemon.jvmargs=-Xmx3g`; фактический
`-Xmx` демона лог не печатает) — три из трёх, тогда как без очереди на 3 ГБ падали три из четырёх;
ни в одном из девяти прогонов нет строки про нехватку памяти. На двадцати ядрах, где линковкам есть где разойтись, очередь стоит
около минуты на четырёх-пяти: в kompot сравнивали с двумя за раз (271/255/228 с против 336/350/281),
потому что без ограничения сборка не доходила до конца. Тёплая сборка берёт линковки из кэша и цены
не платит.

**Выключить** — `sborka.serializeWebLinks=false` в `gradle.properties`. Это для репозитория, который
измерил кучу своего демона и предпочитает минуты; тогда размер кучи — его, и мерить его заново с
каждым новым линкующим модулем — тоже.

**Проверка.** В стенде два wasm-модуля (`:wasm-one`, `:wasm-two`), их линковки пишут, когда начались
и кончились, и перед стартом ждут друг друга до 20 с, чтобы две линковки, которым *можно* идти
вместе, действительно шли вместе. `verifyWebLinks` (часть `check` стенда) требует, чтобы интервалы не
пересекались; CI отдельно гоняет его с выключателем и тогда требует пересечения — это позитивный
контроль, без которого зелёный вердикт мог бы значить «наблюдатель перекрытий не видит». С двумя
слотами вместо одного `verifyWebLinks` краснеет: проверено локально, перекрытие 710 мс.

## `io.github.youndie.sborka.lint`

ktlint, версия инструмента прибита отсюда, сгенерированные исходники исключены.

Версия инструмента прибита, а не оставлена дефолту плагина: на дефолте стиль едет тогда, когда
бампнули плагин, а не тогда, когда решили поменять стиль, — и это ровно тот диф, который никто не
читает.

Второй половиной вопроса занимается `sborka.settings`: ktlint читает `.editorconfig`, поэтому та же
версия инструмента с другим `.editorconfig` — это другой форматтер. `./gradlew updateEditorconfig`
кладёт эталонный, `checkEditorconfig` отказывается от разъехавшегося.

| свойство | по умолчанию | что делает |
|---|---|---|
| `sborka.ktlintVersion` | `1.8.0` | версия **инструмента** (не плагина) |

### `ktlintFormat` роняет компиляцию: `else -> Unit`

Правило ktlint `standard:when-entry-bracing`: если тело хотя бы одной ветки `when` в фигурных
скобках или многострочное, скобки должны быть у всех веток. `ktlintFormat` расставляет их сам — и
ветка `else -> Unit` становится блоком, единственная строка которого — выражение `Unit`. В `when`,
который стоит оператором, а не значением, это неиспользуемое выражение. `sborka.jvm` и `sborka.kmp`
компилируют с `allWarningsAsErrors`, поэтому код, к которому руками не прикасались, после
форматтера не компилируется:

```
e: warnings found and -Werror specified
e: …/WhenBracing.kt:20:13 Expression is unused.
```

**Лечится пустым блоком: `else -> {}`.** В выражении это то же значение `Unit`, в операторе —
ничего, и `when-entry-bracing` его не трогает: он уже в скобках. Писать так сразу дешевле, чем
чинить после форматтера.

Воспроизведено на стенде, ktlint 1.8.0 с эталонным `.editorconfig` (`ktlint_official`), временным
файлом в `stand/jvm-lib` (не закоммичен): `ktlintMainSourceSetFormat`, затем `compileKotlin`.

| `when` до форматтера | что сделал форматтер | `compileKotlin` |
|---|---|---|
| оператор: `1 -> { … }` в скобках, рядом `2 -> log += "two"` и `else -> Unit` | обе ветки в скобках, `else -> { Unit }` | **красная**, строка выше; с `-Psborka.warningsAsErrors=false` — зелёная с тем же `w: … Expression is unused.` |
| тот же, но `else -> {}` | в скобки взята только `2 -> …` | зелёная |
| оператор без веток в скобках, `else -> Unit` | не тронут | зелёная |
| значение функции `: Unit = when …`, `else -> Unit` | `else -> { Unit }` | зелёная — значение используется |

Там же срабатывает `standard:blank-line-between-when-conditions` — пустая строка между ветками,
когда хоть одна многострочная; он компиляции не мешает. Найдено при подключении `sborka.lint` к
kompot (youndie/kompot#199): после одного `ktlintFormat` перестали компилироваться восемь модулей.

### kapkan — правила, которые едут вместе с форматтером

`sborka.lint` кладёт на конфигурацию `ktlintRuleset` координату `io.github.youndie.sborka:kapkan`
той же версии, что и сам плагин. Ручки нет: репозиторий, получивший `sborka.lint`, получил правила.

Каждое правило кодирует **один класс дефекта, найденный в этом стеке**, и несёт ссылку на item.
Какие из шести правил брифа написаны, какие пришли после него и почему правила про `@Test` здесь
нет — в [kapkan.md](kapkan.md).

| правило | что ловит | найдено в |
|---|---|---|
| `kapkan:foreign-import-in-common` | `java.*`, `javax.*`, `android.*`, `org.w3c.*` в `common…`-сорс-сете | shashki B-01. Компилятор ловит то же самое — этот ловит на сорок секунд раньше, и ловит в модуле, у которого таргеты только JVM и Android |
| `kapkan:native-identifier` | имя, которое Kotlin/Native не примет (`Name contains illegal characters`), — на деле запятая в имени теста в обратных кавычках — в сорс-сете, который компилирует натив: `common…`, `native…`, `ios…`, `linux…` и любой незнакомый. JVM-, Android- и веб-сорс-сеты не судятся | telek B-01, B-02 и kompot B-69: JVM-прогон `commonTest` зелёный, CI красный на `compileTestKotlinLinuxX64` / `compileTestKotlinIosArm64`. Правило было записано текстом в двух скиллах и пяти `CLAUDE.md` — и третий раз случился при нём |
| `kapkan:swallowed-failure` | `runCatching`, чью неудачу **никто не читает** — в цепочке нет ни `onFailure`, ни `getOrElse`, ни `fold`, а то, что осталось, выбрасывает сам язык; `catch (e: Exception\|Throwable)`, чьё тело ни разу не упоминает `e` | shashki B-39: сериализация отчёта падала, и `runCatching` внутри `launch` это глотал |
| `kapkan:cancellation-swallowed` | в suspend-контексте: `runCatching`, а также `catch (e: Exception\|Throwable)`, из которого отмене не выйти — ни перехвата `CancellationException` с пробросом впереди, ни `throw e` в конце, ни `ensureActive()` | mani (youndie/mani-kotlin-fullstack#164): `UseCase.withTry` заворачивал отмену в `Result`, экран рисовал её как сбой сети, а корутина продолжала работать. Рядом нашлось ещё три, одно — 401 клиенту, который уже ушёл |
| `kapkan:wall-clock` | `System.currentTimeMillis()`, `Clock.System.now()`, `Instant.now()` и соседи из `java.time` | shashki B-29: клиент вычитал серверный дедлайн из собственных часов, и ноутбук на час вперёд рисовал обратный отсчёт, который не начинается |
| `kapkan:suppression-needs-a-reason` | подавление правила kapkan без причины | не находка, а условие: этой аннотацией исчерпывается вся настройка инструмента |

**`swallowed-failure` и `cancellation-swallowed` — не одно правило, хотя издали похожи.** Первое
спрашивает, *прочитана ли* неудача; второе — *имела ли* одна конкретная неудача право становиться
значением. Все четыре находки mani читали свою неудачу безупречно, поэтому первое смотрело прямо на
них и молчало. Обратное тоже бывает: `runCatching` внутри `withContext(NonCancellable)` — находка
первого правила и не находка второго.

**Хелпера `suspendRunCatching` sborka не поставляет,** хотя правило называет его в тексте.
Восьмистрочная inline-функция в `commonMain` потребовала бы мультиплатформенной публикации на
compile-classpath каждого потребителя — публикации такого рода в этом репозитории нет ни одной, и
заводить её ради восьми строк дороже, чем скопировать их. То же рассуждение, что про `@Kapkan.Allow`
ниже.

**`System.nanoTime()` в `wall-clock` намеренно нет.** Это монотонные часы: из них нельзя вычесть
чужой epoch, значит дефекта B-29 они дать не могут. Включение добавило бы семь подавлений по
портфелю, и все семь мерили бы длительность.

### Подавление — одно, и оно обязано объяснять

```kotlin
@Suppress("ktlint:kapkan:wall-clock", "this is the Clock port; everything else reads it")
```

Своей аннотации нет и не будет: `@Kapkan.Allow` в `commonMain` потребовал бы мультиплатформенного
артефакта на compile-classpath каждого модуля каждого репозитория, а `@Suppress` уже везде. Первую
строку проверяет сам ktlint — его правило `internal:ktlint-suppression` отказывается от id, который
не называет ни одного загруженного правила. Вторую требует `kapkan:suppression-needs-a-reason`:
меньше трёх слов — это ярлык, а не причина, и десяток трёхсловных отговорок он знает по именам.

**Побочный эффект первой проверки — это сторож проводки.** Файл с подавлением линтуется только пока
jar с правилами реально доехал до воркера ktlint; `stand/gradle-plugin/src/main/kotlin/stand/Kapkan.kt`
существует ровно для этого, и убранная строка `ktlintRuleset` красит стенд с сообщением
«Ktlint rule with id 'ktlint:kapkan:wall-clock' is unknown or not loaded».

## `io.github.youndie.sborka.test`

JUnit Platform, читаемый в логе провал, платформа JUnit и — главное — проверка, что каждый
объявленный `@Test` был выполнен.

**Версия JUnit из каталога — это версия, на которой идут тесты.** `kotlin("test")` резолвится в
`kotlin-test-junit5`, а тот тащит свой Jupiter и по умолчанию выигрывает. Поэтому
`enforcedPlatform`, а не `platform`. Если `sborka.junitVersion` не задан, не подключается ничего:
прибивать JUnit, который репозиторий не называл, — ошибка того же класса в другую сторону.

**Каждый объявленный `@Test` должен был выполниться.** JUnit 5 не запускает `@Test`, возвращающий
значение, и не предупреждает: метод просто не тест, а класс отчитывается на один меньше. Kotlin даёт
написать такое случайно — тело-выражение берёт тип от последнего выражения, а
`kotlin.test.assertNotNull` возвращает то, что проверил. Три таких нашлись по случайности в
репозитории, откуда взята проверка; два прожили месяцы, и один покрывал дефект, который мог обнулить
остаток абонента.

**Объявленное читается из исходников той компиляции, что дала задаче классы**, а не из всего `src/`
модуля: для `jvmTest` мультиплатформенного модуля это `jvmTest` и `commonTest`, но не `nativeTest`.
Иначе одноимённые классы из разных source set-ов — законные, раз их не видит ни одна компиляция
разом, — сливались под одно имя, и выигрывал тот файл, до которого обход каталогов дошёл последним.
Так katcher краснел на одних раннерах и зеленел на других на одном и том же коммите: `jvmTest`
требовал три теста от класса, в котором их два, потому что три было в нативном тёзке. Если задачу
не удаётся сопоставить ни с одной Kotlin-компиляцией, читается весь `src/`, а имя, объявленное в
двух файлах, не проверяется и называется в логе — отчёт JUnit именует суиту `FooTest[jvm]` без
пакета, и выбрать один из файлов значило бы угадывать.

**А суита, не прогнавшая ничего, не проходит.** Сравнение выше требует JVM-овский `Test`: ему нужны
классы, которые скомпилировала именно эта задача, а нативный тестовый бинарь — один исполняемый файл
без class-файлов. Поэтому `linuxX64Test`, `iosSimulatorArm64Test`, `wasmJsBrowserTest` и `jsNodeTest`
получают меньшую, но не пустую проверку: сколько кейсов задача записала в JUnit-XML, и ноль — провал.
Пустая суита зеленее упавшей, и это ровно та форма, в которой wasm-таргет выглядит проверенным и не
является им; проверка приехала из репозитория, где её пришлось написать руками в корневом билде.

Пропущенная Gradle-ом задача (`NO-SOURCE`, или выключенная, потому что на машине нет браузера) свой
`doLast` не выполняет — так что чекаут без браузера собирается, а сказать, что именно пропущено,
обязан репозиторий, а не конвенция.

| свойство | по умолчанию | что делает |
|---|---|---|
| `sborka.junitVersion` | — | версия JUnit BOM; без неё платформа не навязывается |
| `sborka.declaredTests` | `true` | `false` — выключить проверку выполненности |

## `io.github.youndie.sborka.publish`

Всё, что портфель узнал про доставку артефакта потребителю. Пять рукописных копий этого было по
репозиториям, и никакие две не знали одного и того же — каждая дырка находилась одинаково: спросив у
сервера, резолвится ли оно, сильно позже зелёной сборки.

Что делает:

- репозиторий `wip` с креденшелами из окружения;
- `sourcesJar` там, где есть `java`;
- **регистрирует публикацию для `kotlin("jvm")` и для `java-platform`.** KMP-плагин регистрирует свои
  сам, а обычный Kotlin/JVM — нет: без этого модуль собирается, его `publish` отчитывается об успехе
  и не выгружает **ничего**. Exit-код Gradle это от успешной публикации не отличает;
- **атрибут `org.gradle.jvm.version` на jvm-вариантах KMP-модуля.** Обычный `kotlin("jvm")` получает
  его даром от java-плагина, KMP — нет, и берут потребители именно эти варианты. Без атрибута Gradle
  нечем отказать слишком старому потребителю: резолв проходит, компиляция проходит, а падает загрузка
  класса с `UnsupportedClassVersionError`, называя версию байт-кода, а не библиотеку;
- **имя `.aar` с версией.** Из сборки он выходит названным по модулю и больше никак;
- POM, выведенный из одного свойства `sborka.repository` вместо копии в каждом репозитории — три
  строки `scm` это ровно то, что вставляли с ошибкой.

| свойство | по умолчанию | что делает |
|---|---|---|
| `sborka.repository` | — | `owner/name` на GitHub; без него POM не заполняется |
| `sborka.description` | — | одна строка описания в POM |
| `sborka.inceptionYear` | — | год в POM |
| `sborka.jvmFloor` | `17` | самая старая Java, на которой потребителю можно быть |
| `sborka.snapshotRepository` | reposilite `/snapshots` | куда публиковать; только абсолютный http(s), иначе сборка останавливается |
| `sborka.licence` | `MIT License` | |
| `sborka.developerId` / `sborka.developerName` | `youndie` / `Pavel Votyakov` | |
| `sborka.central` | `false` | публиковать ли на Maven Central: добавляет javadoc-jar и подписи |
| `sborka.portal` | `false` | читает не плагин, а `portal.yaml`: репозиторий — Gradle-плагин, который публикуется на Plugin Portal |

`sborka.jvmFloor` — не то же самое, что тулчейн, и по умолчанию ниже намеренно: JDK, которым
библиотеку собирают, — не тот JDK, на котором её будут запускать. Репозиторий, поднявший это не
подумав, отбирает библиотеку у всех потребителей ниже нового пола и узнаёт об этом от них.

### Maven Central — один рубильник и один издатель

`sborka.central=true` применяет плагин, который делает то, чего reposilite не требует, а портал
требует: javadoc-jar рядом с sources-jar и отсоединённую подпись на каждый файл. Подпись ставится
там, где есть ключ (`ORG_GRADLE_PROJECT_signingInMemoryKey`), а не по второму рубильнику: снапшот
едет в reposilite, которому подпись не нужна, и требовать GPG-ключ ради него — значит завести его
в CI без причины. Релиз без подписи отвергает портал, то есть та половина проверяется тем, чья это
работа.

**Заливает бандл один воркфлоу на весь портфель — `central.yaml` в самой sborka.** Причина не в
дублировании yaml, а в секретах: у личного аккаунта GitHub нет общего хранилища (org-level secrets
бывают только у организаций), поэтому `central.yaml` в каждой библиотеке — это копия токена портала
и подписного ключа в каждом репозитории и ротация, которую надо обойти по кругу и которая тихо
делается наполовину, стоит один пропустить. Здесь они лежат в одном месте и стерегут одну задачу.

Библиотеке для публикации не нужно ничего, кроме `sborka.central=true`. Запуск —
`gh workflow run central.yaml -R youndie/sborka -f repository=youndie/<имя> -f ref=<тег> -f
version=<X.Y.Z>`.

Прогон живёт во вкладке Actions самой sborka, и его `headSha` — тоже sborka, поэтому библиотеку в
списке называет только заголовок: `central youndie/<имя> <X.Y.Z> from <тег>` (`run-name`, #118).
По нему прогон находят и на него ссылаются из release notes; `gh run list -R youndie/sborka
--workflow central.yaml` показывает тот же заголовок. Заголовок собран из входов — он говорит, что
просили, а сделано ли, говорит исход прогона.

**Раннер — Linux, и наличие Apple-таргетов это не меняет.** Kotlin кросс-компилирует их klib на
Linux, а публикуются именно klib'ы; видно на CI любого репозитория портфеля, где job на
`ubuntu-*` выполняет `compileKotlinMacosArm64`. `macos-15` брать только если сборке действительно
нужен Xcode.

Настоящее ограничение рядом другое и остаётся: KMP-модуль публикует корень и все таргеты
**с одного хоста**, иначе корень ссылается на варианты, которых никто не собрал. Это про один хост,
а не про macOS.

**Выпуск остаётся кликом.** `publishToMavenCentral` заливает бандл и оставляет его staged;
`publishAndReleaseToMavenCentral` выпустил бы сам, а версию на Central нельзя ни переписать, ни
забрать. Последний шаг — за человеком, который смотрит на то, что вот-вот станет постоянным.

### Gradle Plugin Portal — тот же издатель, второй воркфлоу

Gradle-плагину Central ничего не даёт: потребитель просит `id("…") version "…"` в `plugins { }`,
и без репозитория это резолвит только Plugin Portal. Публикует туда `portal.yaml` в самой
sborka — по тем же причинам, что `central.yaml`: ключ и секрет портала — одна пара на аккаунт,
и лежать ей в одном месте.

Что нужно репозиторию плагина: применить `com.gradle.plugin-publish` **самому** — с `website`,
`vcsUrl` и `tags` у каждого плагина, которых портал требует, — и поставить `sborka.portal=true`
в `gradle.properties`. Конвенции этот плагин не применяют: его метаданные — дело репозитория, а
конвенция, подтянувшая плагин портала на classpath каждому потребителю, платила бы за один
репозиторий всеми. Версия берётся из `-PVERSION`, как у снапшотов и Central.

Запуск — `gh workflow run portal.yaml -R youndie/sborka -f repository=youndie/<имя> -f ref=<тег>
-f version=<X.Y.Z>`. Перед загрузкой воркфлоу гоняет `publishPlugins --validate-only`: проверки
портала на метаданные отвечают за секунды, и загрузка, которую отвергли бы за отсутствующий тег,
не делается вовсе. Заголовок прогона — `portal youndie/<имя> <X.Y.Z> from <тег>`, по той же причине,
что у Central.

**Первую версию нового плагина портал одобряет руками**, обычно за несколько дней; до этого id
не резолвится ни у кого, а прогон здесь зелёный — он загрузил. Следующие версии одобренного
плагина живут сразу. Загруженную версию, как и на Central, не заменить.

### KSP, который гоняется один раз — по общим метаданным

Модуль, у которого аннотированные типы лежат в `commonMain`, обязан гонять процессор на
`kspCommonMainMetadata`: вывод пер-таргетных задач попадает в платформенный сорс-сет, а метаданные,
против которых компилируется `commonMain` потребителя, его оттуда не видят. Модуль с одним таргетом
этого не замечает; второй таргет у потребителя превращает это в unresolved reference.

Сказать это Gradle — три абзаца скрипта, и в одном репозитории они лежали **побайтово одинаково в
семи модулях**. Цена известна, а не предположена: гонка между KSP и dokka за один каталог правилась
одной и той же правкой в семи файлах, и пропуск любого оставил бы флаку живой.

**Что делает конвенция**, если в модуле есть плагин KSP и на `kspCommonMainMetadata` объявлен
процессор:

* добавляет `build/generated/ksp/metadata/commonMain/kotlin` в `commonMain`;
* заставляет ждать `kspCommonMainKotlinMetadata` всех, кто читает этот каталог **как пути**, а не как
  коллекцию: `compile*`, `dokka*`, `ktlint*`, `*SourcesJar`. Список неполон по устройству —
  dokka нашлась флакой в публикации, ktlint нашлась в стенде, — и `builtBy` вместо него невозможен:
  KSP читает тот же сорс-сет, в который пишет, и Gradle отвечает циклом задачи с самой собой;
* выключает пер-таргетные `ksp*`-задачи: процессора у них нет, а каталог с метаданными они читают,
  и Gradle считает это необъявленной зависимостью между задачами.

**Что остаётся в модуле** — сам процессор и его аргументы.

**Условие — процессор, а не плагин.** Модуль может применять KSP для чего-то другого: в kompot есть
такой — скриншотный процессор над `desktopTest` и ничего над `commonMain`. Для него каждая строка
выше неверна, а выключенная пер-таргетная задача — молча зелёная сборка без генерации. Поэтому
вопрос звучит не «применён ли KSP», а «объявлен ли процессор на `kspCommonMainMetadata`»; это факт о
модуле, а не флаг, который надо не забыть выставить.

Модуль, у которого процессоры есть **и там, и там**, конвенция не обслуживает и говорит об этом
вслух: сборка падает с перечислением конфигураций и просьбой развести это руками. Молчаливая
альтернатива — отобрать у него генерацию и оставить зелёные тесты, скомпилированные ни против чего.

Модуль, который уже развёл это руками, называется в корневом `gradle.properties` списком путей —
`sborka.kspHandWired=:shared-ui` — и конвенция его не трогает вовсе. Список путей, а не флаг: отказ
существует ради того, чтобы модуль, выключивший проводку, был назван. Без этой ручки «разведите руками»
было невыполнимо — проверка падала раньше, чем модуль успевал что-то сделать (так в shashki).

Оба случая стоят в стенде: `:kmp-ksp` — обслуживаемый, `:kmp-ksp-platform` — контроль, который
конвенция обязана не трогать. Оба проверяют не только зелёный выход: тест **пользуется**
сгенерированным кодом, а `verifyKspWiring` / `verifyKspLeftAlone` читают, включены задачи или нет —
на инкрементальной сборке файл от прошлого прогона ещё лежит на диске, и модуль, только что
переставший генерировать, продолжает компилироваться.

## `io.github.youndie.sborka.native-service`

`executable { entryPoint; baseName }` для нативных таргетов и `stageNativeImage` — задача, кладущая
release-бинарь в `build/native-image/` под стабильным именем.

Стабильное имя и есть смысл. `linuxX64()` кладёт вывод в `bin/linuxX64/`, `linuxX64("native")` — в
`bin/native/`; оба варианта разумны, оба в портфеле есть, и Dockerfile, скопированный между
репозиториями, падает на сборке образа с «file not found», называя путь, а не разницу.

**Один нативный таргет — плоско, несколько — по каталогу на таргет.** С одним таргетом это
`build/native-image/<baseName>`, ради чего задача и существует. С двумя обе копии переименовывались
в одно имя в один каталог, и Gradle отказывался: `Entry <name> is a duplicate`. `duplicatesStrategy`
был бы однострочным и неверным решением — он кладёт один из двух бинарей, выбранный произвольно, под
именем, которое не говорит, какой именно; `COPY`, нашедший не тот файл, хуже упавшего. Поэтому
модуль с несколькими таргетами кладёт `build/native-image/<konanTarget>/<baseName>`, и сегмент — имя
**konan-таргета** (`linux_x64`), а не каталога под `bin/`: в том каталоге стоит имя Kotlin-таргета,
то есть ровно та произвольность, которую задача и прячет.

Переход между формами громкий: добавив второй таргет, репозиторий меняет `COPY` в своём Dockerfile,
иначе сборка образа падает с «file not found» в тот момент, когда человек и так правит этот модуль.
`writeNativeDockerfile` для такого модуля пишет путь с сегментом и строку о том, что архитектура
здесь — выбор.

Два пути к образу, и репозиторий выбирает один. **Dockerfile**: `writeNativeDockerfile` кладёт
эталонный на диск один раз, дальше он репозиторный, перезаписывать существующий задача отказывается.
**Образ из сборки**: `nativeImageTar` ниже — без Docker-демона, с проверкой загрузки перед записью.
Второй путь появился по решению владельца (B-33), когда проверка набрала 23 из 23 против `docker run`
([research-native-image](research/research-native-image.md)); первый остаётся для тех, кому рантайм-образ
удобнее читать файлом.

```kotlin
nativeService {
    entryPoint = "ru.workinprogress.myservice.main"
    baseName = "myservice"
}
```

### Образ без Docker-демона: `nativeImageTar`

```kotlin
nativeImage {
    base = "gcr.io/distroless/cc-debian13@sha256:…"   // только по digest: тег отвергается
    ports = listOf(8080)
    // environment: по умолчанию MALLOC_ARENA_MAX=2; labels: версия и коммит — сами
}
```

`./gradlew nativeImageTar` делает по порядку: проверяет, что база названа digest'ом; тянет её из
реестра без демона; кладёт поверх release-бинарь из `stageNativeImage` и спрашивает у файлов образа,
загрузит ли его загрузчик — интерпретатор, каждый `NEEDED` транзитивно (`RUNPATH`, `LD_LIBRARY_PATH`
из конфигурации образа, `ld.so.cache`, каталоги по умолчанию), каждую версию символа; и **только если
загрузит**, пишет OCI-tarball в `build/native-image-oci/<baseName>.tar` (jib-core; время создания и
времена файлов зафиксированы, digest зависит от байтов бинаря). Если не загрузит — сборка падает,
называя файл, того, кто его просит, и digest базы; старый tarball удаляется, чтобы красный вердикт не
лежал рядом с образом, который кто-нибудь запушит. Отчёт — `<baseName>.load-check.txt` рядом.

**Чего проверка не видит, и она пишет это в каждом отчёте**: всё, что открывается через `dlopen`
(модули gconv, NSS на старой glibc), и файлы, которые не библиотеки (корневые сертификаты, зоны).
Зелёный вердикт значит «загрузчик запустит бинарь», не «образ работает».

Задача **не висит на `assemble` и `check`**: она ходит в реестр, а сборка, которая лезет в сеть потому,
что кто-то запустил `check`, падает в поезде. jib-core и сама проверка (`io.github.youndie.sborka:image`)
работают в воркере с собственным classloader'ом и резолвятся при запуске задачи — на buildscript-classpath
потребителя их нет. Configuration cache задача переносит.

### Размер страницы аллокатора: 16 КиБ по умолчанию, и когда нужно 256

Конвенция ставит на исполняемый файл `-Xbinary=fixedBlockPageSize=16`; `allocatorPageSize` меняет
число, `0` оставляет компиляторные 128 КиБ (так на Kotlin 2.4.20,
[`NativeSecondStageCompilationConfig.kt:235`](https://github.com/JetBrains/kotlin/blob/v2.4.20/kotlin-native/backend.native/compiler/ir/backend.native/src/org/jetbrains/kotlin/backend/konan/NativeSecondStageCompilationConfig.kt#L235);
256 было до [KT-68909](https://youtrack.jetbrains.com/issue/KT-68909)). **Размер страницы режет в обе стороны, и сторону выбирает
форма сервиса, а не единообразие портфеля.**

**Много потоков, куча в десятки мегабайт — 16.** Аллокатор Kotlin/Native держит по странице на
класс размеров **на каждый поток**, пока поток жив, поэтому резидентная память идёт за числом
потоков, а не за живой кучей, и никакая настройка GC её не ограничивает: это страницы, а не объекты.
`Dispatchers.IO` наращивает потоки под нагрузкой. Замер на katcher, один бинарь и образ,
`--memory=192m --cpus=1`, 50 одновременных запросов
([katcher#58](https://github.com/youndie/katcher/issues/58),
[KT-89365](https://youtrack.jetbrains.com/issue/KT-89365)):

| страница | RSS в покое | пик | пережил 192Mi |
|---|---|---|---|
| 128 КиБ (компилятор по умолчанию) | 56–68 МБ | 252–329 МБ | **0 из 8**, `exit 137` |
| 16 КиБ | 22–26 МБ | 47–62 МБ | 8 из 8 |

**Мало потоков, куча в гигабайты — 256.** В конце разметки, при остановленном мире, аллокатор каждого
потока и куча вызывают `PageStore::PrepareForGC` для каждого класса размеров (Kotlin 2.4.20:
[`alloc/custom/cpp/PageStore.hpp:24`](https://github.com/JetBrains/kotlin/blob/v2.4.20/kotlin-native/runtime/src/alloc/custom/cpp/PageStore.hpp#L24),
вызов из
[`gc/common/cpp/MainGCThread.hpp:56–69`](https://github.com/JetBrains/kotlin/blob/v2.4.20/kotlin-native/runtime/src/gc/common/cpp/MainGCThread.hpp#L56-L69)):
проходит список занятых страниц до хвоста и по одной освобождает каждую, опустевшую при прошлой
чистке. Это линейно по числу страниц и целиком внутри паузы, а та же куча в страницах по 16 КиБ —
это в шестнадцать раз больше страниц. Замер на in-memory хранилище: около 2 ГБ живой кучи, три
потока, CMS, две сборки вперемешку на одном хосте, по три прогона, 60 с записи:

| страница | пауза p50 | пауза p99 | пик RSS |
|---|---|---|---|
| 16 КиБ | 8,0–10,0 мс | 84–139 мс | 4 237–4 244 МБ |
| 256 КиБ | 0,76–0,83 мс | 8–18 мс | 4 290–4 304 МБ |

Пауза в десять раз короче за 1 % резидентной памяти. Контрольные прогоны сдвигали число размеченных
объектов в 4,7 раза и мусор, созданный за разметку, в 10 раз — пауза не пошла ни за тем, ни за
другим: она идёт за числом страниц и растёт вместе с кучей. Отчёт с контрольными прогонами —
[`youndie/kesh` `bench/reports/b-19`](https://github.com/youndie/kesh/tree/main/bench/reports/b-19);
механизм — в исходниках рантайма по ссылкам выше.

| форма сервиса | страница | что болит |
|---|---|---|
| много потоков, куча в десятки мегабайт | **16** (по умолчанию) | резидентная память под лимитом контейнера |
| мало потоков, куча в гигабайты | **256** (`allocatorPageSize = 256`) | stop-the-world пауза сборщика |

Сервис посередине меряет обе величины — пик памяти по cgroup под своим лимитом и паузу по журналу
GC, — а не выбирает сторону по аналогии. Потоковая цена при 256 КиБ возвращается с каждым потоком,
тронувшим класс размеров, так что большая куча, которую обслуживает сотня потоков, платит обе и
выбирать ей придётся замером.

По умолчанию стоит 16, потому что сервисы, под которые конвенция писалась, — первой формы: у keel,
эталонного потребителя, 13,8 МБ резидентной памяти в покое
([замер](https://github.com/youndie/keel/blob/main/docs/research/measurements-2026-09-16.md)).

## `io.github.youndie.sborka.jvm-distribution`

Модуль, который нужен KMP-сервису, чтобы у него была JVM-сборка, которую **отгружают**, а не просто
`jvm()`-таргет, который компилируется. `application`, Ktor Gradle plugin и zavarnik существуют только
для `kotlinJvm` и к многоплатформенному модулю не применяются — значит `installDist` и AOT-кэш не
могут жить в `:server`, им нужен сосед: применяет `application`, зависит от `:server`, держит один
`main`.

Конвенция несёт `application` и главный класс, отдаёт zavarnik'у URL готовности (по умолчанию
`http://127.0.0.1:8080/health/ready` — маршрут, который монтирует kore) и **отказывается от имени
модуля, ломающего дистрибутив**. Kotlin публикует jvm-артефакт многоплатформенного модуля как
`<module>-jvm-<version>.jar`; модуль, названный `<module>-jvm`, даёт второй jar ровно с таким именем,
оба попадают в `lib/`, и `installDist` падает с `is a duplicate`, называя файл и ни один из двух
модулей. Проверка сверяется с зависимостью, а не с суффиксом: `foo-jvm` — коллизия только тогда,
когда `foo` есть на runtime-classpath.

```kotlin
plugins {
    alias(libs.plugins.kotlinJvm)
    id("io.github.youndie.sborka.jvm-distribution")
    alias(libs.plugins.zavarnik)   // применяет репозиторий, как и razves
}

jvmDistribution { mainClass = "io.github.youndie.myservice.jvm.MainKt" }

zavarnik { training { workload { get("http://127.0.0.1:8080/items") } } }
```

Нагрузка обучения остаётся у сервиса намеренно: прогрев, гоняющий не те маршруты, даёт кэш,
неотличимый от хорошего.

Чего конвенция **не** делает:

* не применяет Kotlin — по той же причине, что и `sborka.kmp`;
* не применяет zavarnik — версия принадлежит репозиторию, а конвенция, несущая плагин, положила бы
  его на build-classpath каждого репозитория, взявшего любую конвенцию sborka;
* **не проверяет JDK.** zavarnik сам отказывается от toolchain ниже 25 на этапе конфигурации, называя
  проект и найденную версию. Второй сторож над одним отказом хуже одного: на зелёной сборке не видно,
  который из них работает.

И одного она нести не может: **два соседних модуля с разными Kotlin-плагинами требуют, чтобы корневая
сборка объявила оба с `apply false`**. Иначе каждый приезжает в своей области классов, общий
`KotlinNativeBundleBuildService` существует дважды, и сборка падает на этапе графа задач сообщением
про два `InstrumentingVisitableURLClassLoader` и ни слова о причине. Это факт о скрипте, к которому
плагин не применяется; в `stand/build.gradle.kts` эта пара стоит с тем же объяснением рядом.
