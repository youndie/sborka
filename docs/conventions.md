# Плагины

Каждый плагин настраивает то, что уже подключил модуль, и **сам не подключает ни Kotlin, ни Compose,
ни AGP**. Модуль пишет `alias(libs.plugins.kotlinMultiplatform)` со своей версией из своего каталога,
а sborka реагирует через `plugins.withId`. Иначе любой апгрейд Kotlin в любом репозитории ждал бы
релиза sborka.

Исключение одно — ktlint: sborka его подключает, потому что «какой ktlint у нас» это ровно то общее
решение, ради которого репозиторий и заведён.

---

## `ru.workinprogress.sborka.settings` — плагин настроек

Применяется в `settings.gradle.kts`. Делает три вещи.

**Репозитории с фильтрами контента.** Репозиторий, объявленный без фильтра, спрашивается о *каждой*
координате, которую резолвит сборка: это лишний round-trip на каждый промах и — что хуже — шанс, что
на чужую группу ответит не тот сервер.

Настроить можно только сторону резолва. `pluginManagement` вычисляется до применения любого
settings-плагина — включая этот, который сам через него и достаётся, — поэтому снапшот-репозиторий
там приходится выписывать руками. Строки в [migration.md](migration.md).

**Каталог `wip`.** Опубликованный каталог версий, которые нескольким репозиториям приходится держать
одинаковыми. Именно `wip`, а не `libs`: `libs` остаётся своим у каждого репозитория.

Версия каталога — версия самого плагина, зашитая в jar при сборке. Второе число, написанное рядом
руками, — это число, которое разъедется.

**Проверка `.editorconfig`.** См. `sborka.lint` ниже. Живёт здесь, а не там, потому что
`.editorconfig` — один файл на репозиторий, значит и проверка одна на репозиторий; проверка, которая
срабатывает только если кто-то не забыл применить модульный плагин к корневому проекту, — это
проверка, которая молча не срабатывает.

| свойство | по умолчанию | что делает |
|---|---|---|
| `sborka.repositoriesMode` | `FAIL_ON_PROJECT_REPOS` | `PREFER_SETTINGS` — для репозитория с таргетами `js`/`wasmJs`: репозиторий для дистрибутива Node объявляет не модуль, а сам Kotlin-плагин, и отказ ловит сборку на репозитории, которого никто в ней не писал |
| `sborka.catalog` | `on` | `off` — не подключать каталог `wip` |
| `sborka.catalogVersion` | версия плагина | взять другую версию каталога |
| `sborka.catalogRepository` | — | дополнительный maven-репозиторий для группы `ru.workinprogress.sborka` |
| `sborka.editorconfig` | — | `custom` — этот репозиторий отличается намеренно, не проверять |

Проверка требует, чтобы файл **начинался** с эталона, а не совпадал с ним целиком. Общие правила
обязаны быть на месте и неотредактированными; что репозиторий дописывает ниже — его дело, и один
такой уже есть: там вендоренная спецификация сравнивается тестами побайтово, поэтому секция
`[docs/spec/**]` выключает для этого дерева правила про пробелы. Требование полного совпадения
заставило бы этот репозиторий отказаться от общего стиля целиком ради одной нужной секции.
`updateEditorconfig` переписывает только голову и сохраняет хвост; файл, голова которого не эталон,
он трогать отказывается — классифицировать чужие строки он не может.

## `ru.workinprogress.sborka.base`

Координата, версия, тулчейн. Подключается остальными; отдельно нужен только приложению, которому не
нужны ни публикация, ни `explicitApi`.

Версия ставится **на проект**, а не только на публикацию, и разница из сборки не видна: имена
архивов берутся из версии проекта, поэтому публикация с полным номером отгружает файлы, названные
запасной версией. Резолв работает — метаданные указывают на правильный url, — а файл просто
неправильно назван по прибытии, и два релиза становятся неразличимы для всего, что читает имена.

| свойство | по умолчанию | что делает |
|---|---|---|
| `sborka.group` | **обязательно** | maven-группа всех модулей репозитория |
| `version` (в `gradle.properties`) | `0.1.0-SNAPSHOT` | голова версии; `-PVERSION` из CI перебивает |
| `sborka.jvmToolchain` | `21` | JDK, которым всё компилируется |

Группа не имеет значения по умолчанию намеренно: шесть модулей одного репозитория когда-то уехали
под группой, выведенной из имени каталога, и это всплыло на аплоаде — PUT не по тому пути, после
того как всё скомпилировалось и прошло тесты.

## `ru.workinprogress.sborka.lint`

ktlint, версия инструмента прибита отсюда, сгенерированные исходники исключены.

Версия инструмента прибита, а не оставлена дефолту плагина: на дефолте стиль едет тогда, когда
бампнули плагин, а не тогда, когда решили поменять стиль, — и это ровно тот диф, который никто не
читает.

Второй половиной вопроса занимается `sborka.settings`: ktlint читает `.editorconfig`, поэтому та же
версия инструмента с другим `.editorconfig` — это другой форматтер. `./gradlew updateEditorconfig`
кладёт эталонный, `checkEditorconfig` отказывается от разъехавшегося.

| свойство | по умолчанию | что делает |
|---|---|---|
| `sborka.ktlintVersion` | `1.8.0` | версия **инструмента** (не плагина) |

## `ru.workinprogress.sborka.test`

JUnit Platform, читаемый в логе провал, платформа JUnit и — главное — проверка, что каждый
объявленный `@Test` был выполнен.

**Версия JUnit из каталога — это версия, на которой идут тесты.** `kotlin("test")` резолвится в
`kotlin-test-junit5`, а тот тащит свой Jupiter и по умолчанию выигрывает. Поэтому
`enforcedPlatform`, а не `platform`. Если `sborka.junitVersion` не задан, не подключается ничего:
прибивать JUnit, который репозиторий не называл, — ошибка того же класса в другую сторону.

**Каждый объявленный `@Test` должен был выполниться.** JUnit 5 не запускает `@Test`, возвращающий
значение, и не предупреждает: метод просто не тест, а класс отчитывается на один меньше. Kotlin даёт
написать такое случайно — тело-выражение берёт тип от последнего выражения, а
`kotlin.test.assertNotNull` возвращает то, что проверил. Три таких нашлись по случайности в
репозитории, откуда взята проверка; два прожили месяцы, и один покрывал дефект, который мог обнулить
остаток абонента.

Не покрывает Kotlin/Native: `iosSimulatorArm64Test` — это `KotlinNativeTest`, а не `Test`, и в
`withType<Test>` не попадает. Записано, а не оставлено на «когда-нибудь выяснится».

| свойство | по умолчанию | что делает |
|---|---|---|
| `sborka.junitVersion` | — | версия JUnit BOM; без неё платформа не навязывается |
| `sborka.declaredTests` | `true` | `false` — выключить проверку выполненности |

## `ru.workinprogress.sborka.publish`

Всё, что портфель узнал про доставку артефакта потребителю. Пять рукописных копий этого было по
репозиториям, и никакие две не знали одного и того же — каждая дырка находилась одинаково: спросив у
сервера, резолвится ли оно, сильно позже зелёной сборки.

Что делает:

- репозиторий `wip` с креденшелами из окружения;
- `sourcesJar` там, где есть `java`;
- **регистрирует публикацию для `kotlin("jvm")` и для `java-platform`.** KMP-плагин регистрирует свои
  сам, а обычный Kotlin/JVM — нет: без этого модуль собирается, его `publish` отчитывается об успехе
  и не выгружает **ничего**. Exit-код Gradle это от успешной публикации не отличает;
- **атрибут `org.gradle.jvm.version` на jvm-вариантах KMP-модуля.** Обычный `kotlin("jvm")` получает
  его даром от java-плагина, KMP — нет, и берут потребители именно эти варианты. Без атрибута Gradle
  нечем отказать слишком старому потребителю: резолв проходит, компиляция проходит, а падает загрузка
  класса с `UnsupportedClassVersionError`, называя версию байт-кода, а не библиотеку;
- **имя `.aar` с версией.** Из сборки он выходит названным по модулю и больше никак;
- POM, выведенный из одного свойства `sborka.repository` вместо копии в каждом репозитории — три
  строки `scm` это ровно то, что вставляли с ошибкой.

| свойство | по умолчанию | что делает |
|---|---|---|
| `sborka.repository` | — | `owner/name` на GitHub; без него POM не заполняется |
| `sborka.description` | — | одна строка описания в POM |
| `sborka.inceptionYear` | — | год в POM |
| `sborka.jvmFloor` | `17` | самая старая Java, на которой потребителю можно быть |
| `sborka.snapshotRepository` | reposilite `/snapshots` | куда публиковать; только абсолютный http(s), иначе сборка останавливается |
| `sborka.licence` | `MIT License` | |
| `sborka.developerId` / `sborka.developerName` | `youndie` / `Pavel Votyakov` | |

`sborka.jvmFloor` — не то же самое, что тулчейн, и по умолчанию ниже намеренно: JDK, которым
библиотеку собирают, — не тот JDK, на котором её будут запускать. Репозиторий, поднявший это не
подумав, отбирает библиотеку у всех потребителей ниже нового пола и узнаёт об этом от них.

## `ru.workinprogress.sborka.kmp` и `.jvm`

`explicitApi()`, `allWarningsAsErrors`, `kotlin("test")` в тестовом сорс-сете. Подключают `base` и
`test`.

**Списки таргетов сюда не входят, и это решение, а не недоделка.** В портфеле 243 объявления таргетов
на 14 репозиториев — крупнейшее на вид дублирование, пока не прочитаны комментарии рядом: один
репозиторий не берёт `macosX64`, потому что Kotlin его задепрекейтил и там ничего никогда не гоняли;
сосед берёт, потому что закрывает по нему вехи; третий ограничен тем, что публикует его
Telegram-зависимость; четвёртый не берёт iOS-симулятор, потому что тестовая задача, которая не может
запуститься, хуже отсутствующего таргета — она выглядит как покрытие. Это четыре разных решения с
четырьмя разными причинами, и конвенция, сделавшая из них одно, убрала бы не дублирование, а четыре
аргумента.

| свойство | по умолчанию | что делает |
|---|---|---|
| `sborka.explicitApi` | `true` | |
| `sborka.warningsAsErrors` | `true` | |

## `ru.workinprogress.sborka.mutation`

Задача `mutationTest`: ломает модуль по одному месту и говорит, чего тесты не заметили. Семь мутаций,
сделанных руками в одном репозитории, нашли два стража, которых не ловило **ничего**, и два теста,
проходивших не по той причине, что написана у них в имени.

**В `check` не входит и входить не должно.** Задача медленная, а её результат — не порог, а список
выживших, каждый из которых читается отдельно. Процент выживаемости так же бессмысленное число, как
процент покрытия. И выживший мутант — гипотеза, а не вердикт: он говорит, что мутацию не заметили, а
не какой рычаг правильно добавить.

| свойство | по умолчанию | что делает |
|---|---|---|
| `sborka.mutationPackage` | **обязательно** | пакет, который мутировать и чьи тесты гонять |
| `-PmutationTarget` | весь пакет | сузить прогон до одного класса или семейства |
| `sborka.pitestVersion` / `sborka.pitestJunit5Version` | `1.25.9` / `1.2.3` | |

## `ru.workinprogress.sborka.native-service`

`executable { entryPoint; baseName }` для нативных таргетов и `stageNativeImage` — задача, кладущая
release-бинарь в `build/native-image/` под стабильным именем.

Стабильное имя и есть смысл. `linuxX64()` кладёт вывод в `bin/linuxX64/`, `linuxX64("native")` — в
`bin/native/`; оба варианта разумны, оба в портфеле есть, и Dockerfile, скопированный между
репозиториями, падает на сборке образа с «file not found», называя путь, а не разницу.

Dockerfile **не генерируется в сборку**: рантайм-образ — это решение про сертификаты, разделяемые
библиотеки и glibc базового образа, и ему место в файле, который человек читает.
`writeNativeDockerfile` кладёт эталонный на диск один раз, дальше он репозиторный. Перезаписывать
существующий задача отказывается.

```kotlin
nativeService {
    entryPoint = "ru.workinprogress.myservice.main"
    baseName = "myservice"
}
```
